# 臺北市樹木地圖與修剪行程設計規格

日期：2026-08-01

## 目標

在既有臺北市行道樹透明化查詢平台加入下列能力：

1. 每筆有有效座標的樹木可開啟 Google Maps 對應位置。
2. 自動取得臺北市公園路燈工程管理處公布的行道樹與公園樹木預定修剪行程。
3. 以保守、可解釋的規則列出「可能受影響樹木」，不得宣稱官方已指定個別樹木。
4. 顯示預定日期、地點、預定數量、施作單位、依據與官方來源。
5. 里長、議員或承商姓名僅在官方來源明確揭露時呈現；未揭露時顯示「官方未揭露」，不得推測。
6. 保持手機友善、無障礙、靜態 GitHub Pages 可部署與自動更新。

## 已選方案

採用「建置期證據整合」方案。GitHub Actions 下載官方開放資料與修剪網頁，保存不可變原始快照，再解析、驗證並產生供 GitHub Pages 使用的靜態 JSON。

未採用的方案：

- 瀏覽器即時抓取：會受跨來源限制、官方網站回應時間與版面變動影響，無法可靠保留證據。
- 人工維護配對：個案可能較精準，但無法符合持續自動更新與可重現需求。

## 官方資料與證據原則

修剪行程入口使用臺北市公園路燈工程管理處「行道樹、公園樹木預定修剪及澆灌行程」頁面。抓取器由入口辨識最新的行道樹與公園樹木修剪頁面，不依賴固定內容識別碼。

每次成功抓取都保存：

- 原始 HTML 快照與 SHA-256、來源 URL、擷取時間、內容類型。
- 解析後的標準化行程 JSON。
- 解析器版本與官方發布／更新時間（來源提供時）。

公開行程欄位如下：

- `schedule_id`
- `category`：`street` 或 `park`
- `start_date`、`end_date`
- `districts`
- `locations`
- `team`
- `work_type`
- `work_detail`
- `planned_count`
- `work_unit`
- `basis`
- `requester_type`
- `requester_name`
- `source_url`
- `published_at`
- `retrieved_at`

`requester_name` 只有在同一份官方行程明載姓名或有可驗證的官方個案識別碼能連結到另一份官方來源時才可填入。只有「里長建議」或「議員案」等文字時，姓名固定為 `null`，介面顯示「官方未揭露」。道路所在里、現任里長或選區議員不得被呈現為該案提議人。當依據為「承商查報」時，施作單位仍只呈現在 `work_unit`；除非來源另有承商提報者欄位，否則 `requester_name` 仍為 `null`。

## 樹木資料與地圖

既有標準欄位 `twd97_x`、`twd97_y` 在公開索引建置時轉換為 WGS84 `latitude`、`longitude`。轉換採 TWD97 / TM2 zone 121（EPSG:3826）至 WGS84（EPSG:4326）。只有通過臺北地區合理範圍與有限數值驗證的座標才會公開。

Google Maps 連結格式為：

`https://www.google.com/maps/search/?api=1&query=<latitude>,<longitude>`

不需要 Google API 金鑰。連結使用新分頁並包含安全的 `rel` 屬性。無有效座標時顯示「無定位資料」，不以地址搜尋替代精確座標。

本次同時納入官方公園樹木資料。公開樹木紀錄增加 `tree_type`（`street`／`park`）與公園名稱欄位；搜尋介面提供全部、行道樹、公園樹木篩選。

## 保守配對規則

配對輸出永遠稱為「可能受影響樹木」。官方行程的 `planned_count` 是整個行程的預定數量，不代表候選清單前 N 筆，也不得任意挑選 N 棵樹。

行道樹配對：

1. 正規化全形／半形、空白、常見標點與臺／台字形。
2. 將行程地點依官方分隔符拆為完整路段詞組。
3. 只有樹木地點包含完整路段詞組時才列為候選。
4. 行程若明載行政區，必須同時相符。
5. 過短、僅為方向或無法唯一辨識的詞組不配對，改顯示「無法可靠對應個別樹木」。

公園樹木配對：

1. 行程行政區必須與樹木行政區相符。
2. 正規化後的公園名稱必須完整相符。
3. 名稱缺失或同區有歧義時不配對。

每個配對包含 `schedule_id`、`tree_id`、`match_method` 與固定說明文字，讓前端清楚標示這是路段／公園名稱推論，不是官方逐株名單。

## 元件與資料流

資料管線拆成可獨立測試的元件：

1. 開放資料抓取器：下載行道樹與公園樹木 CSV，保存不可變快照。
2. 樹木正規化器：統一兩類樹木欄位並保留來源與快照日期。
3. 修剪入口探索器：從官方入口取得最新的行道樹、公園樹木修剪內容 URL。
4. 修剪解析器：把兩種官方表格轉成共同資料契約。
5. 座標轉換器：驗證 TWD97 並產生 WGS84。
6. 保守配對器：產生行程與候選樹木關聯。
7. 網站資料建置器：以暫存目錄原子化產生 manifest、分區樹木資料、行程與配對 JSON。
8. 靜態前端：載入 manifest，依需求延遲載入分區資料與行程。

資料流：官方來源 → 原始快照 → 標準化資料 → 驗證 → 配對 → 靜態 JSON → GitHub Pages。

## 使用者介面

維持現有視覺語言與手機優先版面，加入：

- 搜尋表單的樹木類型篩選。
- 桌面表格與手機卡片的「Google 地圖」動作。
- 有近期候選修剪行程的樹木顯示「可能受修剪影響」標記。
- 可展開的樹木詳情，列出所有相關行程、配對依據與官方來源。
- 獨立「近期修剪行程」區塊，可依行道樹／公園樹木、日期、行政區或地點篩選。
- 行程卡顯示施作單位、依據、提報者資訊狀態、預定數量及官方來源。
- 明顯的資料更新時間與「候選配對並非官方逐株名單」說明。

互動元素使用原生按鈕、連結與可存取標籤；鍵盤可以完成搜尋、翻頁、展開詳情及開啟地圖。

## 錯誤處理與資料安全

- 來源下載失敗：工作流程失敗，不以空檔覆蓋上一份有效快照與網站資料。
- 官方版面變動：必要欄位缺少或表格結構不符時解析失敗，阻止發布。
- 公園資料暫時不可用：保留上一次有效資料；manifest 顯示各來源更新狀態。
- 座標無效：個別紀錄省略地圖欄位，整批流程不中斷；統計無效筆數。
- 行程無可靠配對：保留行程但候選樹木為空，顯示無法可靠對應。
- 前端 JSON 載入失敗：顯示可理解的錯誤與重試按鈕，不顯示錯誤的零筆統計。
- 所有外部文字以 `textContent` 呈現；來源 URL 必須通過臺北市政府允許主機清單。

## 自動化與發布

- 樹木資料每日更新。
- 修剪行程每日更新，以降低每週行程變動延遲。
- 更新工作流程在資料驗證與測試通過後提交衍生資料。
- Pages 工作流程只部署通過網站資料驗證的內容。
- 更新失敗時 GitHub Actions 保留錯誤證據，既有 Pages 版本繼續服務。

## 測試與驗收

單元測試：

- TWD97 至 WGS84 的已知座標、範圍檢查與無效值。
- 行道樹與公園修剪表格解析、民國日期、跨日行程與缺值。
- 路段／公園名稱正規化、歧義拒絕與行政區限制。
- `requester_name` 未揭露時不得由其他欄位推導。
- 公開 JSON 契約與外部 URL 白名單。
- 搜尋、樹木類型篩選、分頁與地圖連結。

整合測試：

- 從固定測試快照完成樹木正規化、行程解析、配對與網站資料建置。
- 來源或解析失敗時不覆蓋上一次成功輸出。
- GitHub Actions 命令、權限、快取與 Pages artifact 契約。

驗收條件：

1. 真實樹木資料可依行政區、路段、公園或樹種搜尋。
2. 有效座標的結果可開啟正確 Google Maps 位置。
3. 官網最新行道樹與公園樹木修剪行程會自動出現在網站。
4. 候選樹木與官方預定數量分開呈現，且有推論警語。
5. 施作單位與依據完整顯示；官方未提供的人名不被推測。
6. 手機卡片與桌面表格皆可使用，核心鍵盤操作可完成。
7. 完整測試、資料驗證與 Pages 部署流程通過。

## 非目標

- 不宣稱候選樹木是官方逐株施工清單。
- 不透過道路位置猜測提案里長或議員。
- 不提供即時工程進度、完工狀態或民眾通報系統。
- 不引入需要金鑰或付費額度的地圖 SDK。
